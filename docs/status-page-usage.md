# 状态页用量口径设计(status-page-usage)

状态页(`/memory/status`)的用量图表曾混排两种统计范围,导致「重启后消耗归零」「小图与每日图对不上」。本文记录调查结论、用户故事与统一口径的决策。

## 背景与问题(调查结论)

状态页六块用量的数据源与范围如下(修复前):

| 图表 | 数据源 | 范围 | 重启后 |
|---|---|---|---|
| Token 分布(按职责) | `runtime.usage`(内存) | 本进程 | **归零** |
| LLM 调用消耗(输入/输出/缓存读) | `runtime.usage`(内存) | 本进程 | **归零** |
| 用量明细表 | `runtime.usage`(内存) | 本进程 | **归零** |
| 静态上下文成本估算 | `runtime.state.teams` + 摘要 | 本进程实时 | 视 warmup |
| 近 14 天每日用量 | `usage.jsonl`(持久化) | host 级 | 保留 |
| 近 12 周日历热力图 | `usage.jsonl`(持久化) | host 级 | 保留 |

根因:**一页混排「本进程内存态」与「host 级持久态」两种范围,且无任何范围标注**。三个症状由此而来:① 重启后消耗类图表归零(内存态),与每日图的历史值(持久态)矛盾;② 「静态上下文成本」(上下文估算)与「每日用量」(实际消耗)是两种不同的度量,并排展示无说明,自然「对不上」;③ 跨进程并跑时,每个面板只看到自己进程的消耗,与目录页/节点页已确立的 host 级心智不一致。

## 用户故事

1. 作为用户,重启 dsh web 后,我希望状态页的消耗图表仍显示历史消耗,不因进程重启归零——消耗是 host 级持久事实,不是进程内临时状态。
2. 作为用户,我想一眼分清每张图表的统计范围:哪些是「近 14 天 host 级持久消耗」,哪些是「本进程实时装载」,不再被混排误导。
3. 作为用户,「Token 分布」「LLM 调用消耗」「近 14 天每日用量」应可对账:甜甜圈合计 = 每日用量各柱合计(同一时间窗、同一数据源);今日柱包含当前进程刚发生的调用。
4. 作为用户,多个 dsh 会话并跑时,消耗类图表应聚合 host 上全部进程的消耗(usage.jsonl 是各进程共享追加的),而不是只显示打开面板的这个进程。

## 决策

- **消耗类图表(Token 分布 / LLM 调用消耗 / 用量明细)统一读 `usage.jsonl`,按「近 14 天」聚合**——与「近 14 天每日用量」同窗、同源,甜甜圈合计恒等于每日柱合计(同一聚合派生的两个视图)。
- **每日用量 / 热力图不变**:usage.jsonl 按 84 天零填充;「近 14 天每日用量」是其中最近 14 天的切片。
- **静态上下文成本保持「本进程实时」**——team 装载与摘要体积是进程内存态(跨进程的装载状态由节点页提供),标题明确标注「本进程」,与消耗类图表分区展示。
- **全部图表标题携带范围**:消耗类带「近 14 天」,上下文成本带「本进程」;图表区加一行范围说明。
- **为什么不「全部本进程」**:跨进程并跑时各面板只见自身消耗,且重启归零违背「记忆系统的消耗」心智;**为什么不「全部 host 实时」**:team 装载是内存态,只有状态文件快照(节点页已提供),消耗是事实数据,天然持久。
- `/lmemory usage`(CLI)保持本进程口径不变——命令是会话内的人操作面,「this process」标注已有;面板是 host 级观测面。

## 机制

- `src/usage-log.ts` 新增 `aggregateWindowTotals(rows, days)`:复用 `aggregateByDay` 的同窗过滤,按职责累计 calls/input/output/cacheRead(零填充日求和 = 真实行求和),保证与每日图**数学恒等**。
- `dashboard()`(index.ts)一次 `readUsageRows()`,派生 `totals`(近 14 天)与 `daily`(84 天);`runtime.usage` 退出面板数据源,只服务 `/lmemory usage`(CLI)与节点页的 calls 快照。
- DTO:`DashboardDto.usage.counters` → `usage.totals`(同形:label/calls/inputTokens/outputTokens/cacheReadTokens);面板 api.ts 镜像同步。

## 验收标准(AC)

- **重启保留**:进程重启后,Token 分布 / LLM 调用消耗 / 用量明细显示历史值(>0),与重启前一致。
- **对账恒等**:甜甜圈中心合计 = 近 14 天每日用量各柱合计(同一 `aggregateByDay(14)` 派生,单测锁定恒等);今日柱包含当前进程新调用。
- **范围标注**:消耗类图表标题含「近 14 天」;静态上下文成本标题含「本进程」;图表区有范围说明行。
- **空态**:近 14 天无任何 usage 行时,消耗类图表显示占位文案(此前「本进程尚无 LLM 调用」改为「近 14 天尚无 LLM 调用」)。
- **契约与视觉**:`aggregateWindowTotals` 单测;web-ui 契约测试 fixtures 更新为 totals;xbrowser 三引擎通过(零 console 错误)。

## 非目标

- 不改 `/lmemory usage`(CLI 会话口径,已有 this process 标注)。
- 不改节点页(calls 快照仍取自本进程 usage 计数,其语义是「该进程的节点活动」)。
- 不做跨主机聚合(usage.jsonl 本就按 host 存放)。

## 二级展开与「今天」图(2026-08-15 交互增强)

### 用户故事

1. 作为用户,我想点击「近 14 天每日用量」的某一天,就地展开该天 24 小时的水平柱状图,看当天消耗在小时维度的分布——不用离开状态页。
2. 作为用户,同一处点击也让「用量明细」表就地展开该天 24 小时的二级表格(表头首列 = 日期,其余列与一级一致),看当天每小时的 calls / tokens / 成本明细。
3. 作为用户,「近 14 天每日用量」每行的 token 合计右侧显示该天的估算成本;每日图底部合计行在总 token 右侧显示近 14 天成本合计。
4. 作为用户,我想看「今天(按自然日,00:00 起)」的 LLM 调用消耗小图,与「近 14 天」口径分开——自然日与滚动 24 小时是不同窗口(记忆活动大表是滚动 24h 口径,此处明确区分)。
5. 作为用户,「今天」小图与「近 12 周日历热力图」同行并排(热力图缩成小图),版面更紧凑。

### 机制(host 端,纯计算、不落盘)

- `src/usage-log.ts` 新增 `aggregateByHour(rows, days, now)`:与 `aggregateByDay` 同窗、同口径的**小时聚合**——近 `days` 个本地自然日 × 24 桶(共 `days×24` 桶,零填充,升序),每桶 `{ day, hour, recall/extract/review, total }`。日聚合 = 小时聚合按日求和,**数学恒等**(对账)。
- `src/pricing.ts` 新增 `estimateDailyCosts(table, rows, days, fallback, now)` 与 `estimateHourlyCosts(table, rows, days, fallback, now)`:按「日」与「日×小时」窗口聚合估算成本(逐行 `costFor`,缺价行计 missing 不静默为 0;零填充窗口的空桶 yuan = 0)。两者与 `estimateWindowCosts` 同窗、同口径,成本依旧**即时计算、绝不落盘**。
- `dashboard()` 组装:`usage.hourly`(近 14 天 × 24 桶,桶内合并该小时 yuan / missingPricingRows)、`usage.costs.daily`(近 14 天逐日成本,与 `usage.daily` 最后 14 天对齐)。两者均为**可选 DTO 字段**——旧 host 进程 + 新面板资产的版本错配下优雅降级(不展开、不显示成本,不白屏)。

### 展示(面板)

- **每日图展开**:点击某日行选中/取消(选中态高亮);选中后该行下方就地渲染 24 小时水平柱状图(每小时一行:小时标签 + 三段堆叠 + 该小时 token 合计;行高收窄 ~40%,与一级行区分)。同一选中态由状态页共享:选中某天后,明细表同步展开该天的二级表格(「也是同样的点击某一天」)。
- **明细二级表**:表头首列「日期」(如 `08-15 14:00`),其余列与一级一致(调用次数 / 输入 / 输出 / 缓存读 / 合计 tokens / 估算成本);24 行 = 该天每小时,数字为该小时三职责合计。成本列取 `hourly` 桶的 yuan;缺价显示 `—(缺价 N 行)`。
- **每日图成本**:每行 metric 右侧新增成本(取 `costs.daily`,`—` 当该天无调用或缺价);卡片底部合计行:近 14 天总 tokens + 总 calls,右侧 `¥totalYuan`(复用 `usage.costs.totalYuan`)。
- **今天小图**:「LLM 调用消耗(输入 / 输出 / 缓存读,今天(按日期))」= 今天自然日的 24 个 hourly 桶按职责汇总,复用 `StackedBars`(与「近 14 天」小图同款)。空态「今天尚无 LLM 调用。」。
- **布局**:今天小图与日历热力图放在独立两列行(`charts-pair`);热力图保持 12 周 × 7 天 84 格、格子随半宽卡片收缩(小图化);`charts-wide` 只留每日图。
- 每日图行/明细行仍是纯 div 交互(role=button + 键盘回车),CSP 下无第三方库。

### 验收标准(AC,增量)

- **小时聚合恒等**:`aggregateByDay` 与 `aggregateByHour` 同日求和恒等(单测锁定);hourly 桶数 = 14×24 = 336,零填充。
- **展开交互**:点日行 → 24 条收窄水平柱出现且数值 = 该日三职责分布;再点同一行 → 收起;点另一行 → 切换。选中某天时明细表出现 24 行二级表(首列日期,列结构与一级一致)。
- **成本展示**:每日图行右侧成本 = `costs.daily[day].yuan`(无调用/缺价显示 `—`);合计行右侧 = `costs.totalYuan`。
- **今天图口径**:仅含今天 00:00 起(本地自然日)的 usage 行,不含昨天行(单测锁定边界);与近 14 天小图并存的零错配。
- **降级**:`hourly` / `costs.daily` 缺省(旧 host)时:每日图无展开、行成本与合计成本不显示、今天图显示「今天尚无 LLM 调用。」(不白屏)。
- **契约与视觉**:`aggregateByHour` / `estimateDailyCosts` / `estimateHourlyCosts` 单测;xbrowser 三引擎:展开/收起、二级表、今天图与热力图同行、零 console 错误。
